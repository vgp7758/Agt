## bg_task 通知 seed 键名修复（本版核心）

**用户观察**：「bg_task 现在退出时看起来是 user 吧？我觉得也可以以工具记录的通知形式（不过现在似乎只有 check_bg_task 工具？）」——用户看到的「user 通知」不是渲染问题，是**合成记录从落地起就是残缺的**。

**根因**：生产侧 `_on_bg_task_done` 用 `"name"` 键构造 rec，消费侧 `_seed_steps` 读 `"tool"` 键 → `toollog` 里工具名恒为 `""` → 投影无名无工具形态。service_exit 一直用 `"tool"` 键所以正常——两类通知的对照让用户发现了不一致。

**历史澄清**：commit 44ae953（seed list 包装修正）的注释宣称「恢复标准 check_bg_task 合成记录（工具名/参数正确）」——**当时只修了 list 包装，键名漂移漏网，注释里的效果从未成立**；三层防御（0565971）同理只兜「不崩」，兜不住「键名对不对」。

**修复后效果**：bg_task 完成通知醒来时，上下文里是一条**带名带参带尾部输出的完整工具记录**（assistant `tool_use` → `tool` 结果配对渲染），与 service_exit 同款。

**为什么不需要新工具**：合成记录的 `tool` 字段本来就是**虚拟标注**（`stop_service` 那条也不是真 stop 调用）——用 `check_bg_task` 作 bg_task 通知的合成名语义正合适，且模型想深挖时还能真的调 `check_bg_task(bg_id)` 拿全量输出。

## 种子缺陷谱系：三层防御 / list 包装 / 键名漂移（历史澄清）

bg_task 通知的 seed 构造**踩过三条独立的故障线**，前两次修复都只解决其中一条、注释却宣称全好——本版才真正闭环：

| 时间 | 提交 | 修的那条线 | 漏的那条线 | 症状 |
|---|---|---|---|---|
| 2026-08-31 | `0565971` | 结构（非 dict 坏 seed 崩轮）→ 三层防御 | 产地 / 键名 | 坏 seed 不再崩轮，但降级包装成 `notice(raw=[...])` |
| 2026-08-31 | `44ae953` | 产地（`seed=[rec]` list 包装 → `rec`） | **键名（`name` ≠ `tool`）** | 注释宣称「工具名正确」，实际工具名恒空 |
| **2026-09-11** | **`1d47b37`** | **键名（`name` → `tool`）** | — | 通知轮终于带名带参带尾部输出 |

**通用教训**：一条链上的「结构正确」「产地正确」「键名正确」是三件独立的事——**注释宣称的效果要能被验证，否则会伪装成已修**（44ae953 的注释就这样掩盖了键名漂移整整 11 天）。三层防御只保证「不崩」，不保证「语义对」。

**三条排障口诀**（逐层递进，见 [用户交互 · seed 契约三层防御](../features/user-interaction.md#seed-契约三层防御非-dict-坏-seed-不再崩唤醒轮2026-08-31bg_task-唤醒轮秒崩修复)）：

1. 「turn_start 落了但无 step ≠ 没触发，是秒崩」
2. 「降级包装出现在上下文 = 仍有产地在产坏 seed」
3. 「合成记录渲染成 user 通知 = 先查 seed 键名，再查是否 list 包装」

**契约基线**：seed 统一四键 `{tool, args, result, reasoning}`——与 `_on_service_exit` / `_drain_notices` 降级包装一致，消费侧 `_seed_steps` 读 `tool`。

## 更新方式

```bash
pip install -U agt-agent && /restart     # pip 用户
# 桌面版：本次未发桌面包，等下个功能版本一起
```

生效后可观察：下次 run_python / run_shell 转后台任务完成时，通知轮里的步骤应显示为 `check_bg_task(task_id=...)` 的完整工具调用形态（而非无名步骤）。
